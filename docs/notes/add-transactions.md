# Add tab: transactions, dashboard and history (how it works)

- **Three screens, one ViewModel class.** `AddScreen` (dashboard, `MainScreens.AddNavigation`), `AddIncomeScreen`/`AddExpenseScreen` and `RecentTransactions` (History) all use `AddViewModel`. Each destination gets **its own instance** (`hiltViewModel()`, not scoped to the graph), so form state isn't shared, and each screen only runs its own listener.
- **Writes are a single Firestore batch.** `FirebaseTransactionServiceImpl.addTransaction` writes the transaction to `transactions/{id}` (the Budget screen queries this collection), a copy to `daily_history/{uid}_{yyyyMMdd}/transactions/{id}`, and merges `totalIncome`/`totalExpense` into the daily doc with `FieldValue.increment`. Expenses are stored as **negative** amounts. Totals are stored as positive values.
- **The daily doc id uses the device's local date** (`ZoneId.systemDefault()`), but `formatFirebaseDate` displays in `Asia/Manila`. That's fine while the user is in the PH. Each add overwrites the daily doc's `date` with the latest timestamp, and the history list is ordered by it.
- **Validation lives in `TransactionRepository.addTransaction`:** amount ≠ 0, title and category must be filled. An empty description is stored as `"---"`.
- **Live reads are `callbackFlow` listeners**, following the `compose-firebase-listeners` skill: one Job per listener in the ViewModel, started on ON_START and stopped on ON_STOP through `ComposableLifecycle`.
  - `overviewJob`: today's doc plus its transactions (`getTodayOverview`, two listeners `combine`d inside `flow {}` so the user check sits inside the flow).
  - `historyJob`: `getDailyTransactionHistory(limit)`.
  - `perDayJob`: one day's transactions for the bottom sheet. It's started when a day is tapped, stopped in `onDismissRequest` and in a `DisposableEffect` (rotation closes the sheet without calling dismiss), and cancelled before a new day starts.
- **Pull-to-refresh on History is a fake 500ms reload** when the listener is already running, because the data is live anyway.
- **History paging uses a growing limit, not cursors.** `historyLimit` starts at 20. `OnLoadMoreHistory` adds 20 and restarts the listener, so the whole list stays one live listener. `hasMoreHistory = size == limit`. Load-more uses `isLoadingMoreHistory` (a spinner row), not `isListLoading`, so the list and scroll position stay on screen. The trigger is `snapshotFlow` on `LazyListState`, within 5 items of the end; `totalItemsCount` is part of the key so it re-checks after each page.
- **Separate loading flags:** `isLoading` = the full-screen LoadingDialog (saving only), `isListLoading` = the skeleton list, `isSheetLoading` = skeletons inside the day sheet. Driving the sheet with `isLoading` used to pop the dialog over it.
- **Double-tap guard:** `OnAddTransaction` returns early if `isLoading`, and sets `isLoading` before `launch`.
- **The History list is grouped by month** with `groupBy` on the loaded days plus `stickyHeader` (`MonthHeader`). A month that's only partly loaded shows a smaller "spent" total until the next page arrives.
- **Overspent = expense > income.** It shows as `colorScheme.error` on the dashboard ring and the history bars, plus an "over" label. With expenses and no income, the progress shows as full.
- **Category list:** `CategoryDropdownButtonModel.list[0]` is `""`, the "nothing selected" start value. The menu and Budget use `list.drop(1)`, and `icons`/`colors` line up with the dropped list.
- **Colors:** the theme is light-only (`Theme.kt` maps `darkTheme -> lightScheme`), so there is no `values-night`. Adding night colors without a real dark scheme gives dark tones on a light UI. Use `verified_green_text` for green **text**, because the base `verified_green` is too light on light backgrounds.
- **Edit / delete entry point:** tapping a `TransactionItem` (its `onClick` is optional) in "Last Added" or the History day sheet opens `TransactionActionsSheet` in a `ModalBottomSheetDialog`. Each screen keeps it as `selectedTransaction` (null = closed), like `selectedDay`. In History it stacks on the day sheet. Edit closes both sheets and stops `perDayJob`; a delete shows live in the still-open day sheet. Delete goes through a `CustomAlertDialog` whose `confirmColor` is `colorScheme.error`.
- **dailyDocId is passed in, not recomputed:** `state.dailyHistory.docId` on the dashboard, `selectedDay.docId` in History. Recomputing it from the transaction's date with the device zone could pick the wrong day after a timezone change.
- **Edit reuses the Income/Expense forms.** The routes are `data class (docId?, dailyDocId?)`, and null means add mode. `LaunchedEffect(docId)` → `OnLoadTransactionForEdit` (a one-shot `getTransactionById`) prefills the form. It's skipped if that doc is already loaded, so rotation keeps unsaved edits. The button is "Update Transaction" and stays disabled until the load is done, so an edit can't be saved as a new transaction. `MainScreen.topBarTitle` reads `toRoute<>().docId` to show "Edit Income/Expense". A `"---"` description is shown as empty and saved back as `"---"`.
- **Edit math:** income stays income, so only one total moves, by `increment(abs(new) - abs(old))`. `oldAmount` is the amount loaded when the form opened. Editing on two devices at once could drift the totals; `runTransaction` would fix that if it ever matters. `date` is never touched, so neither the order nor the time changes.
- **Delete math:** one batch deletes both transaction docs and does `increment(-abs(amount))` on the matching total. The daily doc is kept, so an emptied day shows ₱0 in History. That also means the batch `update` on it never fails with NOT_FOUND.
- **Ownership:** every new service function throws `NoUserException` first (the VM's `onError` then toasts and logs out). `getTransactionById` and `deleteTransaction` treat another user's doc as `DocumentNotFoundException`.
- **Prefill gotcha:** `CurrencyTextField` and `CategoryDropdownButton` keep their own `remember` state, which is read once on the first frame. That frame comes before the async edit load. Each has a `LaunchedEffect` on its input (`amountInCents` / `selected`) that writes values set from outside into the field. It does nothing while the user types or picks, because the value already matches.
- **Known gaps:** `batch.commit().await()` never completes offline, so add, edit and delete leave the LoadingDialog up. A failed edit load leaves the form with Update disabled until the user presses Back.
