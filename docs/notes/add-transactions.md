# Add tab: transactions, dashboard and history (how it works)

- **"Income" is shown as "Allowance"**: money set aside for a category for that day. Only what users see was renamed; Firestore fields (`totalIncome`) and class names (`AddIncomeScreen`, …) are unchanged, so old data still works and old income entries count as allowance. The Add tab is about **today** (no carry-over); ranges live on Budget (`budget.md`). Templates are in `allowance-templates.md`.

- **Three screens, one ViewModel class.** `AddScreen` (dashboard, `MainScreens.AddNavigation`), `AddIncomeScreen`/`AddExpenseScreen` and `RecentTransactions` (History) all use `AddViewModel`. Each destination gets **its own instance** (`hiltViewModel()`, not scoped to the graph), so form state isn't shared, and each screen only runs its own listener.
- **Writes are a single Firestore batch.** `addTransaction` delegates to `addTransactions(list)` (templates add several at once). Each transaction goes to `transactions/{id}` and a copy to `daily_history/{uid}_{yyyyMMdd}/transactions/{id}`, and the daily doc gets one `set(merge)` with `FieldValue.increment` on `totalIncome`/`totalExpense` **and** the per-category maps `expenseByCategory` / `allowanceByCategory` / `countByCategory` (count = expenses only), which Budget reads. The same batch also increments `monthly_history/{uid}_{yyyyMM}` (category maps + per-weekday expense) and sets `inMonthly: true` on the daily doc; edit/delete only touch the monthly doc when that flag is there (`budget-insights.md`). Expenses are stored as **negative** amounts; totals and map values are positive.
- **1.7.0 extras in the same batch (0 extra writes):** `expenseByWallet` per wallet on the daily and monthly docs, and `dayStatusByCategory` (category → "dd" → ok/over/unplanned) on the monthly doc.
  - **Wallet totals** only go on days with `walletTotals: true` (new days, or the backfill), so an edit/delete never takes off an expense that was never counted.
  - **Day marks are set, not added.** Each save recomputes the touched categories from the day doc plus the change: edit/delete reuse the day doc they already read; add reads it with `readDay` (cache first, since the Add tab listens to today, then the server for at most 2s).
  - **Can't read the day** (offline, not cached): the extras are skipped and the next save of that day, or the backfill, fixes them.
  - **Backfill:** `~/Documents/DenuSpend-backfill-backup/backfill-170.js` (outside the repo) rebuilt both for every day before 1.7.0 (dry run 2026-11-27: 208 days, 16 months, 1,243 reads, 224 writes).
- **Wallets:** expenses carry `walletId` ("" = not deducted) and the same batch moves the wallet balance on add/edit/delete; allowance never touches a wallet. Details in `wallet.md`.
- **Category maps are nested maps, not dotted keys:** in `set(merge)` a dot is literal, and a category like "Work/Education" must stay one key. An empty map is never written, because merging `{}` would replace the existing map.
- **The daily doc id uses the device's local date** (`ZoneId.systemDefault()`), but `formatFirebaseDate` displays in `Asia/Manila`. That's fine while the user is in the PH. Each add overwrites the daily doc's `date` with the latest timestamp, and the history list is ordered by it.
- **Validation lives in `TransactionRepository.addTransaction` / `updateTransaction`:** amount ≠ 0, title and category must be filled. `missingFieldsMessage` names what's missing ("Please add an amount and a category"), shown in `ErrorDialog` (which has an OK button). An empty description is stored as `"---"`.
- **Live reads are `callbackFlow` listeners**, following the `compose-firebase-listeners` skill: one Job per listener in the ViewModel, started through `ComposableLifecycle`. **`AddScreen` is a bottom-nav tab, so it has no ON_STOP stop** (CLAUDE.md rule): its listeners keep running so the tab stays cached. History and the forms are pushed screens and still stop on ON_STOP.
  - `overviewJob`: today's doc plus its transactions (`getTodayOverview`, two listeners `combine`d inside `flow {}` so the user check sits inside the flow).
  - **Midnight check:** `OnGetTransactionOverview` returns early only if the job is active **and** `overviewDate == LocalDate.now()`. Otherwise it stops and restarts on the new day. ON_START (tab switch, return from a pushed screen, app foreground, unlock) and pull-to-refresh both send it, so a same-day ON_START costs no reads. Known gap: staying on screen, unlocked, across midnight shows yesterday until one of those happens. Data is still saved to the right day, because the day id is computed at write time.
  - `templatesJob`: the templates doc (see `allowance-templates.md`), same "only if not active" rule.
  - `historyJob`: `getDailyTransactionHistory(limit)`.
  - `todayJob`: today's daily doc only (`getTodayDailyHistory`), for the forms' "Food left today" / "Food today" line. The forms are pushed screens, so it starts ON_START and stops ON_STOP. It's the same doc the Add tab's overview already listens to, so the SDK serves it from that listener (~0 extra reads); a `get()` would cost 1 read every open.
  - `perDayJob`: one day's transactions for the bottom sheet. It's started when a day is tapped, stopped in `onDismissRequest` and in a `DisposableEffect` (rotation closes the sheet without calling dismiss), and cancelled before a new day starts.
- **Pull-to-refresh on History is a fake 500ms reload** when the listener is already running, because the data is live anyway.
- **History coming back from a pushed screen** (Edit) restarts the stopped listener without the skeleton when rows are already loaded (`collectDailyHistory(keepRows)`), so the list and scroll stay. The skeleton + 500ms is only for the first load.
- **"Today by category"** (`ui/add/components/TodayByCategoryCard.kt`, under the Add/Allowance buttons): one row per category with an allowance or spending today, in dropdown order. Each row shows the name + "₱X left/over", with "₱X spent of ₱Y allowance" (or "₱X spent · no allowance") under it, the amounts SemiBold + `onSurface` and the words grey (`String.withStyledParts()`, shared with Home's Today card). It reads `state.dailyHistory`'s category maps (the overview listener, 0 extra reads) and is hidden when empty. Home's Last added and category chips open the Add tab for this. The ring card (`TodayIncomeAndExpensesSection`, 56dp ring) reads "₱X spent / of ₱Y allowance / ₱Z left", with "left" on its own line, because next to the allowance it got squeezed into a thin column with big amounts.
- **Pull-to-refresh on the Add dashboard (`OnRefreshOverview`)** re-sends `OnGetTransactionOverview` + `OnGetAllowanceTemplates` (the midnight / dead-listener checks) and shows `isRefreshing` for 500ms. Budget deliberately has none.
- **History paging uses a growing limit, not cursors.** `historyLimit` starts at 20. `OnLoadMoreHistory` adds 20 and restarts the listener, so the whole list stays one live listener. `hasMoreHistory = size == limit`. Load-more uses `isLoadingMoreHistory` (a spinner row), not `isListLoading`, so the list and scroll position stay on screen. The trigger is `snapshotFlow` on `LazyListState`, within 5 items of the end; `totalItemsCount` is part of the key so it re-checks after each page.
- **Separate loading flags:** `isLoading` = the full-screen LoadingDialog (saving only), `isListLoading` = the skeleton list, `isSheetLoading` = skeletons inside the day sheet. Driving the sheet with `isLoading` used to pop the dialog over it.
- **Double-tap guard:** `OnAddTransaction` returns early if `isLoading`, and sets `isLoading` before `launch`.
- **The History list is grouped by month** with `groupBy` on the loaded days plus `stickyHeader` (`MonthHeader`). A month that's only partly loaded shows a smaller "spent" total until the next page arrives.
- **Overspent = expense > allowance.** It shows as `colorScheme.error` on the dashboard ring and the history bars, plus an "over" label. With expenses and no income, the progress shows as full.
- **Category list:** `CategoryDropdownButtonModel.list[0]` is `""`, the "nothing selected" start value. The menu and Budget use `list.drop(1)`, and `icons`/`colors` line up with the dropped list.
- **Colors:** the theme is light-only (`Theme.kt` maps `darkTheme -> lightScheme`), so there is no `values-night`. Adding night colors without a real dark scheme gives dark tones on a light UI. Use `verified_green_text` for green **text**, because the base `verified_green` is too light on light backgrounds.
- **Edit / delete entry point:** tapping a `TransactionItem` (its `onClick` is optional) in "Last Added" or the History day sheet opens `TransactionActionsSheet` in a `ModalBottomSheetDialog`. Each screen keeps it as `selectedTransaction` (null = closed), like `selectedDay`. In History it stacks on the day sheet. Edit closes only the actions sheet, so the day sheet is still open on Back: the open day is a `rememberSaveable` docId looked up in the live list, the sheet's `LazyListState` is hoisted (`TransactionDialogContent(listState)`), the day sheet opens full height (`ModalBottomSheetDialog(skipPartiallyExpanded)`), and ON_START restarts `perDayJob` for it (read through `rememberUpdatedState`). Restarting the same day keeps its rows (`AddViewModel.perDayDocId`), so the scroll comes back. A delete shows live in the still-open day sheet. Delete goes through a `CustomAlertDialog` whose `confirmColor` is `colorScheme.error`.
- **dailyDocId is passed in, not recomputed:** `state.dailyHistory.docId` on the dashboard, `selectedDay.docId` in History. Recomputing it from the transaction's date with the device zone could pick the wrong day after a timezone change.
- **Edit reuses the Income/Expense forms.** The routes are `data class (docId?, dailyDocId?)`, and null means add mode. `LaunchedEffect(docId)` → `OnLoadTransactionForEdit` (a one-shot `getTransactionById`) prefills the form. It's skipped if that doc is already loaded, so rotation keeps unsaved edits. The button is "Update expense / allowance · ₱X" and stays disabled until the load is done, so an edit can't be saved as a new transaction. `MainScreen.topBarTitle` reads `toRoute<>().docId` to show "Edit Income/Expense". A `"---"` description is shown as empty and saved back as `"---"`.
- **Edit math:** income stays income, so only one total moves, by `increment(abs(new) - abs(old))`. Category maps: same category → that key moves by the delta; changed category (`EditTransactionRequest.oldCategory`) → `-old` on the old key, `+new` on the new one, and the count moves too (expenses).
- **Negative-value guard:** incrementing a missing map key creates it, so decrementing on a day saved **before** the maps existed would leave a negative value in Budget. Edit and delete first `get()` the daily doc (`hasCategoryTotals`, 1 extra read) and skip the maps if it has none. All existing days were backfilled on 2026-11-21, so the guard now only matters for docs written by older app versions. `oldAmount` is the amount loaded when the form opened. Editing on two devices at once could drift the totals; `runTransaction` would fix that if it ever matters. `date` is never touched, so neither the order nor the time changes.
- **Delete math:** one batch deletes both transaction docs and does `increment(-abs(amount))` on the matching total (and on the category map + count, behind the same guard). The daily doc is kept, so an emptied day shows ₱0 in History. That also means the batch `update` on it never fails with NOT_FOUND.
- **Ownership:** every new service function throws `NoUserException` first (the VM's `onError` then toasts and logs out). `getTransactionById` and `deleteTransaction` treat another user's doc as `DocumentNotFoundException`.
- **Every transaction has two copies with one id:** `transactions/{id}` and `daily_history/{day}/transactions/{id}`. Versions from Mar 20 to Jun 21, 2026 wrote only the day copy, so edit (the form's `getTransactionById`) and delete were denied by the `transactions` rules (`resource.data.userId` of a missing doc). On 2026-11-23 a create-only script (`~/Documents/DenuSpend-backfill-backup/backfill-top-level-transactions.js`) added the 83 missing top-level copies. If a PERMISSION_DENIED shows up on old data, first check that both copies exist.
- **Prefill gotcha:** `CurrencyTextField` keeps its own `remember` state, which is read once on the first frame. That frame comes before the async edit load. It has a `LaunchedEffect` on `amountInCents` that writes values set from outside into the field. It does nothing while the user types or picks, because the value already matches. `TitleNoteFields` likewise opens the note once the loaded note arrives (`LaunchedEffect(hasNote)`), and keeps it open if the text is cleared.
- **List controls** (`TransactionListControls.kt`): All / Allowance / Expense, Amount (biggest first, tap again for latest) and By category (headers in dropdown order), on "Last Added" and the History day sheet. They work on the device because those lists are fully loaded; display-only, kept in `rememberSaveable`. On the dashboard the chips are a `stickyHeader` in the one scrolling list (the today card and buttons scroll away). **Not done on purpose:** sorting the paged History *days* by amount, which would fight the growing-limit date paging.
- **`TransactionItem`** keeps the title, and shows the category icon plus a "category · description" subtitle (blank and `"---"` parts dropped, one line).
- **Writes use `awaitWrite(context)`, never `.await()`** (`utils/network/FirestoreWrite.kt`, since 1.2.0). Firestore applies a write to the cache at once, but its Task only completes when the server confirms. That never happens offline, so the LoadingDialog used to stay up.
  - Offline, it doesn't wait: the form closes and the write syncs later.
  - Online, it waits up to 10s, so real errors (rules, a wallet closed meanwhile) still reach `onError`. Wi-Fi without real internet waits the full 10s and then counts as saved.
  - A queued write that fails later is only logged.
  - It needs `ACCESS_NETWORK_STATE` (declared in the manifest).
  - Reads before writes (the edit/delete guard `get()`s) still `await()` and are served from the cache offline. An uncached doc shows the normal error.
- **Known gaps:** A failed edit load leaves the form with Update disabled until the user presses Back.
- **The forms** (`AddExpenseScreen` / `AddIncomeScreen`) share components in `ui/add/components/`: `AmountInputSection` (centered amount with an inline "-₱"/"+₱" prefix via `CurrencyTextField(inlinePrefix)`, +₱50…1,000 chips that add to the amount, the info tooltip), `CategoryGrid` (3×3 tiles from `CategoryDropdownButtonModel.list.drop(1)`), `TitleNoteFields` (title 20, optional 2-line note 50, counters; Enter becomes a space), `FormSectionHeader`, and `FormSaveBar`. Layout: `Column(imePadding) { scrolling form (weight 1f); FormSaveBar }`, so only the form scrolls and Save stays pinned. **Keyboard insets:** targetSdk 36 forces edge-to-edge on Android 15+, where `adjustResize` no longer shrinks the window, so `imePadding()` is required there. `MainScreen`'s content Box does `.padding(padding).consumeWindowInsets(padding)`, otherwise the nav bar height is counted twice and shows as a gap above the keyboard. Removing `imePadding()` hid Save under the keyboard on API 35 (tested in 1.2.1). Expense also has `WalletPickerRow` (see `wallet.md`). Allowance has no templates (the dashboard sheet handles those).
- **Today line math** (from `todayJob`'s doc): Expense "left" = allowance − spent for the category (+ the original amount when editing today's expense in the same category), then − the typed amount. Allowance: today's allowance → today − original (same category, edit) + typed. Editing another day's transaction hides the line. Before the first snapshot it can briefly show ₱0.00 (accepted).
- **Strings:** all Add UI text is in `strings.xml` (since 1.2.0). Category names in `CategoryDropdownButtonModel` stay hardcoded on purpose, because they're Firestore keys.
- **The expense form's category hint** (`leftTodayText`) sits under the "Category" header, right above the grid (`FormSectionHeader(supportingText)`, the same for the allowance form's `allowanceTodayText`). It used to be under the amount, but you type the amount first and then scroll down to pick a category, so the hint was off screen right when it changed. It never shows a negative "left". It reads "Food left today: ₱A → ₱B", "Food overspent today: ₱X → ₱Y", or "Food left today: ₱A → overspent by ₱B", always with positive amounts.
