# Navigation & session (how it works)

- **Login state is state; only AppRoot turns it into navigation.** `MainViewModel.session` (`Loading / LoggedIn / NeedsWalletSetup / LoggedOut`) is created Activity-scoped in `AppRoot.kt`. AppRoot has a top-level NavHost (`AppRootScreens.SplashTopLevel / AuthTopLevel / WalletSetupTopLevel / MainTopLevel`), and one `LaunchedEffect(session)` navigates there with `popUpTo(graph.id){inclusive=true}`.
- **Why navigate instead of `when(session)`:** popping a back stack entry clears every ViewModel inside it, including the nested NavHost's screens. A plain `when` leaves them alive in the Activity store (NavHost doesn't clear on dispose, checked in the nav 2.8.0-beta04 source). Keep the top-level NavHost.
- `AppRootScreens` is deliberately **not** a `NavigationScreens`, so no ViewModel can `OnNavigate` to it.
- **Login:** `AuthViewModel` sends `OneTimeEvents.OnLoginOrRegisterCompleted` after login/register fully finishes → `LoginScreen`/`RegisterScreen` `onLoginOrRegisterCompleted` → `MainViewModel.onLoginOrRegisterCompleted()`. It's explicit because Firebase signs in *before* `RegisterUseCase` saves the display name.
- **Auth world (`AuthNavHost`):** Login ⇄ Register switch with `PopUpTo(current, inclusive)`. Forgot password is *pushed* on top of Login (`ForgotPasswordNavigation(email)`, no PopUpTo), so Back returns to Login. `AuthViewModel` reads that `email` arg from `SavedStateHandle` to pre-fill the field.
- **Logout:** never navigate. Just call `profileRepository.logout()` (or delete the account). `MainViewModel.observeSignOut()` (Firebase `AuthStateListener` through `AuthService.observeAuthState()`) sets LoggedOut and clears DataStore. `NoUserException` handlers just call `logout()`.
- **Startup:** `MainViewModel.checkCurrentUser()`. A network error still means LoggedIn if Firebase has a cached user. A signed-in user without a physical wallet goes to NeedsWalletSetup first (`loggedInOrSetup()`, `wallet.md`), also after login/register.
- **Inner navigation:** screens get `onNavigate(route, NavOptions?)` / `onPopBackStack`. VMs send `OnNavigate(route, NavBehavior)`, and screens call `event.behavior.toNavOptions()` (`navigation/NavBehavior.kt`). `NavBehavior` = `None | PopUpTo(dest, inclusive)`.
- **Shell (`MainScreen.kt`):** one Scaffold. The top/bottom bar visibility, the title and the selected tab are all derived from `currentBackStackEntry` with `hasRoute`/`hierarchy`. Never keep a separate "selected tab" variable. Tabs use the standard `popUpTo(start){saveState}` + `restoreState`. The name/photo come from `MainViewModel.user` (a DataStore flow).
- **A screen that switches tabs** (e.g. Home's cards) gets `onNavigateToTab` = `MainScreen`'s `navigateToTab`, passed through `AppNavigation` → `addMainNavGraph`. Never `navigate()` to a tab route directly (`home.md`).
- **Adding a screen with a title:** add a branch in `topBarTitle()` plus a string under `<!-- MAIN SCREEN -->`. If it's in a new graph and needs the top bar, add it to `showTopBar`.

## Details from the navigation refactor (PR #1, 2026-11-18)
- **Sign-ins are ignored by `observeSignOut()` on purpose.** Firebase signs you in partway through registration, before `RegisterUseCase` saves the display name. Switching to Main then would clear `AuthViewModel` and cancel that save, so only sign-outs switch the world, and login goes through `OnLoginOrRegisterCompleted`.
- **`NavBehavior.toNavOptions()` is the only place a behavior becomes `NavOptions`.** `ClearAll` was removed (only login/logout used it). Don't hand-build `NavOptions.Builder` in screens.
- **A new `OneTimeEvents` type needs a branch in every exhaustive `when`.** 7 screens have one (e.g. `OnLoginOrRegisterCompleted -> {}`), so adding an event breaks their build until each gets a branch.
- **Tabs:** `MainScreen.kt` has a private `BottomTab` list. `route = null` shows a tab as disabled (Wallet, Goals) until it's built. Tab screens (Home, Add, Budget) show **no back arrow** (`isOnTabScreen` in `canNavigateBack`). Back on a non-Home tab goes to Home through a `BackHandler` that calls the same `navigateToTab` as the bottom bar (saveState/restoreState), so the tab's ViewModel and live listeners survive. A plain `popBackStack()` would destroy them. Tab screens never stop listeners on ON_STOP (CLAUDE.md).
- **Top bar user info** comes from the `MainViewModel.user` DataStore flow, so a name or photo change shows right away. A photo that fails to load is local UI state (`photoFailed`). Photo URLs are saved as `photoUrl?.toString().orEmpty()`, never the string `"null"`.
- **Splash** is a plain composable with no ViewModel and no delay. It shows only while `checkCurrentUser()` runs.
- **Left as-is:** `TokenProvider` (`di/modules/`) is still used by `HomeViewmodel` for the name toast, and isn't live-updating. `DenuSpendApp.instance` was removed, so use Hilt's `@ApplicationContext` instead.
- **How to check for the leak:** put a `Log.d` in a tab ViewModel's `onCleared()`, open that tab, then sign out. It should log right away. If it only logs when the app closes, the worlds aren't being popped.
